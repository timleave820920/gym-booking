# 设计工作流（design-system）

本项目的需求→设计全流程。文件：`DESIGNS-INBOX.md`（收件箱/状态）→ 设计文档（`<功能名>设计方案.md`，根目录）→ `DEV-BACKLOG.md`（开发任务清单）。

设计阶段只产出文档和原型，**不写业务代码**（界面原型 HTML 例外，可进 `web/`）。

## 一、录入（用户消息以 design：/design: 开头）

1. 钩子已自动把原文追加到 `DESIGNS-INBOX.md` 头部。若未落盘（钩子未生效/旧会话），用 Read 检查后手动补充。
2. **先 Read `DESIGNS-INBOX.md`**，确认该条编号（#Dn）；编号如与钩子生成不一致则以文件为准。
3. **追问澄清**（AskUserQuestion 或直接问，一次问全，最多两轮）：
   - 给谁用？（学员/教练/管理员）解决什么问题？
   - 核心交互是什么？（页面/入口/关键操作流）
   - 范围边界：一期做什么、明确不做什么？
   - 有参考（竞品/设计稿/图片）吗？
   - 优先级：P0/P1/P2？
   需求仍模糊 → 保持 ⬜ 待澄清，**禁止直接开写**。

## 二、设计（需求清楚后，标 📐 设计中）

产出**一份**设计文档 `docs/designs/<功能名>设计方案.md`（若 docs/designs 不存在则放根目录）：

1. **需求描述**：一句话目标 + 用户场景 + 验收标准（可测）
2. **界面设计**：
   - 页面结构：页面路径、入口、导航
   - 每个页面的布局（文字描述或 ASCII 草图）
   - 交互细节：点击/滑动/弹窗/空态/错误态/加载态
   - 复用 `DESIGN-SYSTEM.md`（品牌色 #F9F4DF/#B9FF66/#5B57EB、字号、间距）；已有页面尽量复用组件样式
   - 可生成 `web/` HTML 原型供用户预览（可选，复杂界面建议做）
3. **程序架构**：
   - 涉及的表/字段变更（对照 `DATA-MODEL.md`，金额一律分 fen）
   - 后端接口清单（路径、方法、参数、返回；对照 `server/index.js` 路由表风格）
   - 前端页面/组件清单、数据流（哪个接口喂哪个页面）
   - 配置单源（member-config/energy-config/shop-items 等已有模式）
   - 幂等/并发/事务要点（若涉及支付/订课/候补，参照 CONVENTIONS.md 强制规矩）

## 三、确认（最关键闸门）

把设计文档**关键部分**（界面方案 + 架构方案）展示给用户，用 AskUserQuestion 或直接问：

- 界面这样 OK 吗？（有改动点就改文档）
- 架构这样 OK 吗？（数据模型/接口清单）
- 优先级确认

**用户确认前不写入 DEV-BACKLOG，不写任何业务代码。**

## 四、写入开发任务

用户确认后：

1. 把设计文档里的工作拆成任务（每任务 = 一次可提交的小步，含验收标准）写入 `DEV-BACKLOG.md`「待开发」区，每条引用 `DESIGN #Dn`、标优先级 P0/P1/P2
2. `DESIGNS-INBOX.md` 该条标 `✅ 已确认（DEV-BACKLOG，设计文档: xxx）`
3. 回复用户：「设计完成并已确认，任务已写入 DEV-BACKLOG。说『开始dev』即可开工」

## 五、边界

- 设计阶段**禁止**动业务代码（miniprogram/ server/ 的 .js/.wxml/.wxss），只允许改文档、DESIGNS-INBOX.md、DEV-BACKLOG.md、web/ 原型
- 需求与现有功能冲突/重复 → 先指出再设计
- 涉及钱/签到/会员 → 先对照 CONVENTIONS.md 与 BUG-LEDGER 相关教训
- 用户跳过确认直接说「开始dev」→ 视为确认（记录到设计文档：用户直接授权）
