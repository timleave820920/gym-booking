# Bug 工作流（bug-system）

本项目的 bug 全流程管理。文件：`BUGS-INBOX.md`（收件箱/状态）↔ `BUG-LEDGER.md`（正式台账，五要素）。

## 一、录入（用户消息以 bug：/bug: 开头，或说"报bug/记录bug"）

1. 钩子已自动把原文追加到 `BUGS-INBOX.md` 头部。若未落盘（钩子未生效/旧会话），用 Read 检查后手动补充。
2. **先 Read `BUGS-INBOX.md`**，把该条状态标为 ⏳ 或保持待确认，编号如与钩子生成不一致则以文件为准。
3. **描述不清就追问**（AskUserQuestion 或直接问，一次问全）：
   - 哪个页面/哪个功能（页面路径）？
   - 现象是什么 vs 期望是什么？
   - 怎么复现（操作步骤）？在开发者工具还是真机？
   - 有报错文案/toast 吗？
   无法定位（缺页面或现象）的 bug 保持 ⬜ 待确认，**禁止瞎修**。
4. **只登记，不修复**：录入阶段到此为止——回复用户「已登记（编号 #N）」，然后停下等待，**即使描述清晰也禁止动手修**。必须等用户明确说「修bug / 开始修 / 处理这些bug」才进入第二阶段（2026-08-15 用户要求：报 bug 后不要立刻修，等叫才开始）。

## 二、批量修复（用户授意后，如"修bug""开始修""处理这些bug"）

授意 = 一次性批准整批。之后**静默逐一执行，不再逐个确认**，但每个完成后给一行简短汇报。

对每个待确认/待修复条目：

1. **定位**：按描述找到页面/接口/代码；必要时读数据/日志复现。先看 `BUG-LEDGER.md` 是否已有同类根因（防重蹈覆辙）。
2. **修复**：只改该 bug 相关代码；遵守 `CONVENTIONS.md` 强制规矩（金额规则、签到语义 B1-B3、接口契约等）。
3. **测试**（必须完整输出+退出码，禁止 grep 掩盖失败）：
   - 改动的 JS：`node --check`
   - 后端改动：`DB_PATH=/tmp/gym-test-clean-$$.db node minitest/run-tests.js`（干净库模式，全绿）
   - 前端改动：相关页面语法/逻辑自查；真机类问题说明需 L3 手测
   - 新接口：run-tests.js 至少 1 条断言 + coverage.test.js 探针（强制规矩 #4）
4. **更新台账**：
   - `BUG-LEDGER.md` 新增条目（倒序，最新在上）：现象/根因/修复/回归测试/防护层 五要素 + 编号
   - `BUGS-INBOX.md` 该条标 `✅ 已修复（BUG-LEDGER #N）`
5. **git 提交**：`git add` 相关文件 → commit（格式 `fix: 简述（中文）`，引用 `BUG-LEDGER #N`）。pre-commit hook 会自动再跑全量测试，红则修。
   - **不 push**（除非用户明确要求）
6. 一行汇报：`#N 已修复+测试通过+已提交`。

## 三、边界

- 描述不清/无法复现 → 停下问用户，不猜。
- 修复涉及资金/订单/签到语义 → 先对照 CONVENTIONS.md 规则，风险大先说明再动手。
- 用户说"只修某条" → 只处理指定编号。
- 全部完成后：列出剩余待确认条目（如有）。
